# Payload features (detail)

Moved verbatim from `payload/CLAUDE.md`. The summaries there keep the rules that must always be known.

## Cache stamp

**Cache stamp** (`globals/CacheStamp.ts`, `hooks/cacheStamp.ts`): `afterChange`/`afterDelete` hooks set the global `cache-stamp` (`changedAt`) in the transaction of the change, once per request; the web containers poll it and empty their page cache and memos (`website/CLAUDE.md`, Cache clearing). Only collections and globals in `STAMPED_COLLECTIONS`/`STAMPED_GLOBALS` stamp: **a new collection or global that changes a public page must be added there** (votes, reactions, stats and Bon games stay out: they write all the time and would keep the cache empty). `comments` stamp only when a public (published) comment appears, changes or leaves (hidden): held-for-review comments and the counter updates of votes and reports (`skipCommentHooks`) do not. `redirects` (a plugin collection) gets the same hooks through `overrides` in `redirects.ts`; `tests/cacheStamp.test.ts` fails when a collection or global of the config is neither stamped nor on its explicit not-public list. The stamp global has no hooks of its own. A migration that seeds through the Local API before the `cache_stamp` table exists (older than `20261127_113328_cache_stamp`) must set `context: { skipCacheStamp: true }`, or a fresh database fails to migrate.

## Retention job

**Retention job** (`src/jobs/retention.ts`, daily 03:30 UTC, only where `PAYLOAD_RUN_JOBS=true`): clears name and mail of accepted/rejected suggestions 90 days after their last update and of never-handled (`new`) ones after 365 days (via `db.updateMany`, so the lock hook does not block it). Deletes removed, hidden, pending (never approved) and self-deleted comments 183 days after their last update, with their votes and reports; a comment with replies is blanked like a self-delete instead (vote and report counters reset to 0, also for already self-deleted ones, so `updatedAt` moves on). It also removes the `visitor` hash of `word-feedback` rows 395 days (13 months) after their last update; the answers stay. `updatedAt` is the clock for all of this except reports (no separate timestamp). It also clears the e-mail of open reports 90 days after creation (`createdAt` is the clock); closing a report clears it at once. A failing comment is logged and skipped, the task then fails. The periods are promised in the privacy policy; change both together.

## Admin stats

**Admin stats** (`/admin/stats`, `components/StatsView.tsx`, nav link `StatsNavLink`): any logged-in user (a visitor without a login is sent to the login); range and choices live in the URL (`von`, `bis`, `reihen`, `ansicht` = linie|flaeche, `verteilung` = reaktion|nutzung, shown as the „Feedback-Diagramm“ row; parsed by `lib/statsParams.ts` / `lib/statsRange.ts`, `statsHref` is its inverse). Nothing asked: last 30 days. A `bis` in the future is cut to today, a range over 366 days loses its oldest days, garbage or reversed dates give the last 30 days; the page says so in a notice. Above 90 days the chart groups by ISO week. `lib/statsQueries.ts` `loadStats` sums the daily series per Berlin day in raw SQL (`word_stats`, `word_feedback` with a reaction, published `comments`, `suggestions`, finished `bon_games`) plus range totals (reaction split, top lists: views, „Beliebt“ = like share, „Typisch berlinerisch“ = „say“ share, both from `MIN_GROUP` votes). Totals count every word, also trashed and draft ones; only the top lists show published, untrashed words. Every tile and the comparison chart use the equally long range before (`previousRange`, loaded with `tops: false`); if only that one fails the page still shows. Raw SQL bypasses Payload access and hooks and its table/column names must follow any rename (`statsQueries.test.ts` checks the columns exist); `num()` throws on a non-number instead of showing „NaN“. Charts are Chart.js on a canvas (`components/stats/StatsCharts.tsx`, colors read from the admin CSS variables in `themeColors.ts`). `trending()` is separate and unchanged (reactions count there, the usage survey does not).

## Word page data

**Word page data**: `words` has `stress`, `grammar` (`plural`, `diminutive`), `examples` (rows may carry `contributorName` and `contributorSuggestion` like `facts`/`related`: a public credit under the example, same privacy-policy note), `facts` (rich text `text`, `source` of exactly that entry, shown before the credit) and `related` (rows may link the contributing suggestion; `contributorName` is a public credit under the entry, hidden from MCP and not covered by the 90-day clean-up of suggestions: name it in the privacy policy; an MCP update replaces `examples`/`facts`/`related` wholesale (the MCP row schema has no `id`), so `mcpKeepCredits` merges the stored `contributorName` back by row index (moving or deleting rows via MCP can shift a credit to its neighbour; MCP drafts are reviewed before publishing); a `related` row without a word keeps saving after its word was deleted (FK set null), only new rows need a word or label); `affiliate.books[].themen` ties a book to Themen; global `word-page` holds the Jeschichten question (`storyPrompt`, must contain `{Wort}`). The old origin text `infoText` and the word-wide `sources` are gone (migration `20261123_201659_drop_word_info_text`): the migration `20261123_190000_info_text_to_facts` copied them into `facts` (kind herkunft) on the v18 deploy; its `up` is now empty, its `down` still removes the unedited copies.

## Suggestions → words

**Suggestions → words** (`hooks/adoptSuggestion.ts`, `lib/suggestionEntry.ts`, `hooks/suggestionLock.ts`, `lib/wordMatch.ts`; `type`, `kind`, `relation` etc. are nullable in the database and enforced by `validate`): creating a suggestion or changing its Berliner Wort fills `similarWords` (same `matchKey` spelling, without its own word; a failing search is logged and skipped). **Setting the status to `accepted` takes effect at once, in the suggestion's transaction** (any error rolls the status back): `type: word` without a `word` creates the word **published** and links it (an empty or taken slug is refused with 400; a hand-chosen `word` is only linked, nothing is merged); `example`, `fact` and `related` append a row (with `contributorName` = suggester and `contributorSuggestion`; a fact's text becomes plain rich-text paragraphs) to the live `targetWord` and republish it, and the cache stamp follows. The word row is locked (`for no key update`) while the entry is added, so two accepts at once keep both rows. These types refuse with a readable 400 when the word is trashed, gone, never published or has newer unpublished draft changes (publishing would put unreviewed edits live), when the text is blank or a kind/relation is unknown, when the suggestion is created already accepted (the credit needs its id: save first), and when the same suggestion is already in the word with other text; a name is cut to 40 characters (the credit field). Accepting over MCP is refused for every type with a 403 (`adoptSuggestion`; `mcpDraftOnly` would refuse the publish anyway). `refuseBulkAccept` (`beforeOperation`) refuses a bulk update that sets `accepted` with a 400: accept one by one. Only the change _to_ `accepted` triggers; saving an accepted suggestion again adds nothing. A suggestion is locked while its linked `word` is published: derived from the word's `_status` (virtual field `lockedByWord`), so a new-word suggestion is locked right after accepting, and withdrawing or deleting the word unlocks it; `example`/`fact`/`related` use `targetWord`, never `word`, and stay editable. The `update` access makes a locked one read-only in the admin (REST/MCP get a 403); `refuseWhenLocked` is the backstop with a readable message for bulk and Local API updates. Deleting stays possible.
