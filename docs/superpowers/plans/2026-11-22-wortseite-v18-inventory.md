# Wortseite v18: Inventory (PR 0, read-only)

Status: draft for the owner's approval. Nothing is deleted or changed by this document. Later PRs read it for field names, endpoint shapes and the delete list.
Method: code only (codebase-memory graph, then reads). No database, no `.env*`, no user-written content was read. Paths are relative to the repo root; `file:line` points at the code the row is about.
Target: SPEC §1, §7, §8, §13, §18, §21 of the handoff (`wortseite-v18/SPEC.md`), design `docs/superpowers/specs/2026-11-22-wortseite-v18-design.md`.

Short version of what matters most (details below):

1. `comments` publishes new rows immediately (only links hold them). Jeschichten must be reviewed first, so the hook has to change (Risk R1).
2. `comment-votes` means „Hilfreich / Nich hilfreich“ today, not agree/disagree. Do not carry the old votes over (Answer A1).
3. „Stimme zurückziehen“ clears only `usage`; „Alle meine Antworten löschen“ deletes the cookie's rows over all words. Neither is the per-word „Stimme und Angaben löschen“ of SPEC §7.4 (table 4).
4. `suggestions.word` is the lock key (a live word locks the suggestion). The plan's „target word in the existing `word` relation“ would lock every new example/fact/related suggestion at once (Risk R3).
5. No Thema-to-book mapping exists (Answer A2). Trend rank/change/views7 exist for the weekly top 10 only; „Im Aufwind“ has no page-side data yet (Answer A3).

## 11. Risks

**R1. Jeschichten would be published unreviewed.** `applyRules` sets a site-created comment to `published` unless a link is present (`payload/src/collections/Comments.ts:47-49`; default `status` `published` at `:179`). SPEC §8.1/§13 promise review before publication. Task 8 must create new Jeschichten as `pending` (needs a hook change: `applyRules` overrides `status` on every create without `req.user`), and the editor mail wording („Neuer Kommentar“, `Comments.ts:89-91`) should change. Also: when the page switches, all existing `published` comments become visible as Jeschichten with only the link filter behind them (SPEC §21.7): the owner should confirm that is fine or decide on a one-time review.

**R2. Stats SQL depends on `comments`.** `collect()` counts published `comments` rows per `word_id`/`created_at` with weight 3 (`payload/src/lib/wordStats.ts:141-145,151`) and `statsQueries.ts:143` counts them per day. Replies are counted too. New columns are safe; renaming `comments`, `word_feedback` or their columns breaks trending, home stats and admin stats (`wordStats.ts:126`, `homeStatsLoad.ts:24,89,162-165,317`, `statsQueries.ts:35-36,80-107`, test `payload/tests/statsQueries.test.ts`). Adding `suggestions.type` rows inflates the per-day suggestions series (`statsQueries.ts:144`, filter is `true`) and the mail subject „Wortvorschlag“ (`Suggestions.ts:22`).

**R3. `suggestions.word` is the lock key.** `isLockedByWord` locks a suggestion while its `word` is published (`payload/src/hooks/suggestionLock.ts:11-27,33-50,53-54`), and `adoptSuggestion` creates a draft word when status becomes `accepted` with `word == null` (`payload/src/hooks/adoptSuggestion.ts:59`). The plan (Task 4) puts the target word of an `example`/`fact`/`related` suggestion in that same relation: such a suggestion would be read-only the moment it is created for a live word, and editors could not set `accepted`/`rejected`. Use a separate relation (for example `targetWord`) or make the lock conditional on `type === "word"`. `berlinerWord` and `translation` are `required` today (`Suggestions.ts:59-60`, NOT NULL columns): the migration must drop NOT NULL, and its `down` must remove or backfill non-word rows before restoring it.

**R4. MCP exposure.** `suggestions` is readable and updatable over MCP (`payload/src/mcp.ts:30-36`); only `userName`/`userMail` are hidden (`Suggestions.ts:63-68`). New free-text fields from visitors (`text`, `relatedText`, `highdeutsch`, any contributor name) will be readable by the model: put any name or contact field behind `notOverMcp` and keep `reports` (optional e-mail) and `comments` out of the MCP list. `facts[].contributorName` on `words` would be readable and writable through the `words` MCP tools (`mcp.ts:25-29`); decide whether names belong there.

**R5. Retention does not know the new data.** `retention.ts` clears suggestion name/mail after 90/365 days, comments after 183 days, feedback visitor after 395 days (`:7-10`), and the privacy policy promises these periods („Speicherdauer“, comment at `:6`). `reports.email` (cleared on close in the plan) needs the same treatment for reports that are never closed, and a new `suggestions.authorTag` needs a clear date.
